## 🔴 `DOC-VOCAB-1` · RESERVE "WERKBON". THE COLLISION IS ALREADY LIVE.

**One word, two documents, today:**
```

projects-management/bordereau/[id]    <h1>Werkbon</h1>  (:81)     ← WRONG. This is a bordereau.
```

**This is defect shape #1 in the vocabulary layer** — two representations of one *word*. It is cheaper to fix than the code version and exactly as damaging if left: a crew asking for "the werkbon" and a bookkeeper asking for "the werkbon" would be asking for different documents, and nobody would notice until one of them was wrong.

| Word | Document | Generated from | Contains |
|---|---|---|---|
| **Bordereau** *(de chantier)* | Site job sheet | **a project** | tasks, site instructions, sign-off lines. **No financials — deliberate.** |
| **Bestelbon / PO** | Material purchase request | **a project** | materials, quantities, delivery info, supplier acknowledgement |
| **Werkbon** | Field/work report | **a clock entry** | hours, what was done, and *conditionally* client signature + field-service data |

- [ ] **`bordereau/[id]` stops calling itself a Werkbon.** Title becomes **Bordereau** / *Bordereau de chantier* — nl/fr/en/ro through the catalogue, **not a literal** (`LOC` rules).
- [ ] **Check `nl.json`:** `Uren / Werkbonnen` and `viewTimesheet: "Werkbon bekijken"` are **correct** — they are the timesheet. `viewWorkOrder: "Werkbon bekijken"` needs checking: **which document does it open?**

### 🛑 THE DESIGN QUESTION THIS RAISES — Florin decides
**Today both are *views*: they render from current project data every time they open. "Draft" implies they become *records*.** Those are different things, and the difference matters per document:

| | **View** (today) | **Record** (what "draft" implies) |
|---|---|---|
| Content | always current | a **snapshot** of when it was issued |
| Needs | nothing | numbering · status · storage · revisions · archiving |
| Layer | L3, exists | **`R4` document engine** |

**Planner recommendation — they are not the same:**
- **Bordereau → stays a VIEW.** A site sheet should show *today's* tasks. A snapshot from three weeks ago is actively misleading on a building site, and the crew wants what is true now. **Printing one is not issuing a document.**
- **Bestelbon → becomes a RECORD.** It goes to a **supplier**, who will deliver and invoice against it. **What you ordered, at what price, on what date, must not change afterwards** — same argument as archive-before-send and the export lock. It needs a number, a status *(draft · sent · confirmed · delivered)*, and an archived PDF.

**If that split is accepted, "draft bordereau" at handover means "the view is ready to print", and only the bestelbon is genuinely a draft record.**

# 🎨 LAYOUT PROPOSAL — Planner, 2026-09-21
**Florin's rule: *"less complicated is better than more complicated in this case."*** Taken literally throughout.

## The recommendation in one line
**No preview/edit tabs. No second rendering path. The working screen IS the document, and printing strips the chrome.**

### Why not tabs
A "printable view" tab and an "actionable items" tab are **two representations of one document**. They can disagree, the user must remember which one is authoritative, and every change needs to appear in both. **That is the defect we remove everywhere else — it should not be introduced on purpose here.**

**The codebase already does it the right way**, in three places: `bordereau:56` · `po:55` · `timesheets/[id]:129`
```jsx
<div className="… print:hidden">          {/* chrome disappears when printing */}
<div className="max-w-[210mm] … A4-page">  {/* the document */}
@media print { … }
```
**One screen, one truth, `Cmd+P` gives exactly what you are looking at minus the buttons.** No new rendering path to build or keep in sync.

# 🔧 `PANEL-1` · RECONCILE THE TWO INPUT SURFACES — Planner 2026-09-21

**Florin, 2026-09-21:** *"In the quote/invoice engine there is a side panel that has more power over the document than the grid view… I found myself using it, especially on the purchase invoices, and I like the function. We just need to reconcile the two input surfaces — the panel was intended to be the grid properties available without exiting to the grid… and should be wider."*

## 🟢 GOOD NEWS FIRST — the panel is NOT a hand-built drift
```jsx
{/* DB Properties Panel — shows all record fields including Excel-imported ones */}
<DbPropertiesPanel databaseId={invoicesDbId} pageId={id} … />   // ClientInvoiceEngine:1823
```
It is the **generic, schema-driven** panel. **The intent Florin remembers was implemented.** So most of the "divergence" is by design:

| | Shows |
|---|---|
| **Panel** | **every property in the schema** |
| **Grid** | only the **active view's visible columns** (`PropertiesDropdown`) |

**That is correct behaviour, and it is why the panel feels more powerful — it is the only surface showing the whole record.** `structuredComm` and the document title are editable there because they are in the schema but hidden from the grid view. **Nothing to reconcile.**

## 🔴 THE REAL DEFECT — relations resolve in the grid and silently do not in the panel
```js
// GRID — RelationColumn:74 + :107-108
const targetDatabase = getDatabase(relationDatabaseId);
// Fallback: Query pageIndex for entries belonging to relationDatabaseId
const indexEntries = Object.values(pageIndex).filter(e => e.databaseId === relationDatabaseId);

// PANEL — DbPropertiesPanel:429-431
const targetDb = databases.find(db => db.id === relationDatabaseId);
const unselected = targetDb ? targetDb.pages.filter(...) : [];      // ← NO FALLBACK
```
**The grid falls back to `pageIndex` when the target database is not hydrated. The panel returns empty.** So *"no client set"* and *"the clients database has not been loaded this session"* look identical — **`LAZY-2`'s rule (not-loaded must never look like empty), unfixed one level down.**

**A second candidate produces the same symptom** and has the same fix: `relationDatabaseId` seeded **bare** (`db-clients`) in `mockData` while `DatabaseClone` seeds it **resolved**. A bare id matches no database for a tenant whose instance is `db-clients-cmneyas2`. *(This one is an `R1` instance — identity by bare id.)*

### The fix
- [ ] 🔴 **One relation resolver, used by both.** Extract the grid's path — *store, then `pageIndex` fallback, then resolve through the seraph* — into a single function. **`RelationColumn` and `DbPropertiesPanel` both call it.** Two surfaces resolving relations two ways is the defect shape; **one resolver ends it.**
- [ ] **Distinguish the three states**: a relation with no value · a relation whose target is not loaded · a relation whose target genuinely has no records. **Never render all three as an empty box.**
- [ ] **Report which cause is real** for `client` on purchase invoices before fixing — bare id, unhydrated, or both. **Do not fix speculatively.**

### While in there
- [ ] **Widen the panel.** `ClientInvoiceEngine:1823` — `w-80 lg:w-96`. Florin uses it daily on purchase invoices; **make it comfortable.** Consider resizable and remembering the width (`useUserPreferences`).
- [ ] **Do not move fields between panel and grid.** The split is correct. **What is wrong is the resolution, not the layout.**
