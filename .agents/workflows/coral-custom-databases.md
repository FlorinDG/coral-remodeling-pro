# CORAL — CUSTOM DATABASES — scaffolded down the stack — Planner 2026-09-18

**Florin, 2026-09-18:**
> *"I am not in a rush for the feature, but we go logical. Does it need anything present in the kernel? Does it need to talk to the core? We scaffold always following this logic, and then we implement it at seraph level. When gating instantiates it, it goes to module gate, because not all tiers will have access. Then write the leaf."*

**This is the method, and it is the exact inverse of how the codebase got here.** Every defect we have chased — three blob readers, five write doors, four cron traversals, `en-US` dates — was written leaf-first, and the layer beneath it was inferred afterwards or never. **Scaffolding downward first is what stops the next one.**

Applied here as the worked example. **Not scheduled.** Sits behind promotion and `R1`.

---

## L0 · KERNEL — does it need anything?

**Almost nothing, and that is the point.** One primitive, and it does not exist yet.

- [ ] **`mintDatabaseId()` — server-side identity minting.** Today `store.ts:60/865/875` calls `uuidv4()` **in the browser**. A database's identity is currently generated by the client that happens to be creating it.
- [ ] The minted id must be **unique**, **tenant-scoped**, and **unable to collide with a system logical key** — a tenant naming a database "Invoices" must never shadow `db-invoices`.
- [ ] **Nothing else.** No storage, no messaging, no new computation. The formula engine, the block tree, the DnD sensors are all already there and already generic.

**Test of the layer: would another feature want this?** Yes — **`R1`'s `logicalKey` and `R5`'s job identity need the same guarantee.** That is what makes it kernel rather than feature code.

## L1 · ERP CORE — what must it talk to?

Three things, and **all three are already required by work that is queued**:

- [ ] **Provisioning as a callable capability** — `createDatabase` becomes a **server action** that mints identity, registers the database, and returns it. **The browser loses the ability to bring a database into existence.**
  *Already required by:* `R1` A5 · `coral-module-entitlement-model.md` `E2` (provision on trial opt-in) · free-tier `G1` (provision on upgrade). **Four features, one capability.**
- [ ] **Schema validation** — properties declared, types valid, formula references resolvable, relation targets existing. `F1`'s rule ("nothing undeclared") becomes enforced rather than remembered.
- [ ] **Read/write path** — **nothing new.** `saveRecord()` (`R2-1`) and `usePagesOf` serve a custom database exactly as they serve `db-invoices`. **If they don't, that is an `R2` defect, not a custom-database one.**

## ⛨ SERAPH — implement it here

**A custom database is the first thing in the system born after the gate exists**, which makes it the cleanest test of whether the gate works.

- [ ] **Created only for the acting tenant.** The tenant is **never a parameter** — it comes from the session. `R1-3`.
- [ ] **Listed and opened only by its owner.** `resolveDatabaseId` must handle a custom id the same way as a system one: **a lookup that fails closed**, not a name match.
- [ ] **`logicalKey` is NULL for custom databases** — they have no type, only an identity. **This is the cleanest argument for `R1-1b`'s two-column split**: system databases have both *what kind* and *which instance*; custom ones have only *which instance*. **One string cannot carry both, and a custom database is where that stops being theoretical.**
- [ ] **`isSystemDatabase()` must return false** — and `schema-cleanup` must therefore never touch it. *(Today `GARBAGE_NAMES` deletes by display name. A user calling their database "New Workspace" would lose it.)*
- [ ] 🔴 **The negative isolation suite gets its sharpest case:** *tenant A creates a custom database; tenant B must not see it in any list, search, index, export or job.* **If the gate holds for a database that did not exist when the gate was written, it holds.**

## ⛨ MODULE GATE — gating instantiates it

- [ ] **`DATABASES` already exists** in `PLAN_MODULES` (PRO, ENTERPRISE, FOUNDER, CUSTOM — **not FREE**) and in `MODULE_ROUTE_MAP` as `'databases' → 'DATABASES'`.
- [ ] ⚠️ **But `/admin/dynamic-db` is ungated today** — no `verifyModuleAccess` anywhere in it. **The module entry exists and nothing enforces it.**
- [ ] **Entitlement at the data door, not only the route** — `requiredModuleForDb` returns `null` for a custom database, read as *"deliberately ungated"*. **That is the third fail-open default**, and a custom database is the case that makes it matter.
- [ ] **A per-tier count limit** — how many custom databases per tier. 🛑 **Florin decides the numbers.** Enforced **server-side at creation**, never by hiding the button.
- [ ] **Unavailable = absent.** FREE sees no Databases module at all — not a locked screen. *(Florin, 2026-09-16.)*

## L3 / L4 · THE LEAF — written last, and it is the smallest part

**Everything visual already exists.** 20 property types incl. `formula`/`rollup`/`relation`, a 255-line formula engine with a 637-line reference, 12 column types, 6 view types, filters, sorts, the block editor, `NotionGrid`.

- [ ] **A real create flow** — name it, then create. *(Today `dynamic-db:26` sends `'New Database'`, which `store.ts:816` rejects as garbage. **`SCHEMA-1a` killed the button it was protecting.**)*
- [ ] **A list of the tenant's custom databases**, with switching. *(Today the page renders `databases[0]`, hardcoded.)*
- [ ] **Reachable schema editor** — add/rename/retype columns. `DatabaseClone` already does this; custom databases simply sit outside `isLockedSchemaDB`.
- [ ] Rename · duplicate · delete, with confirmation and a count of what is being deleted.

## WHAT THE WALK-DOWN REVEALS

| Layer | New work |
|---|---|
| L0 | **1 primitive** — and `R1`/`R5` want it anyway |
| L1 | **2 capabilities** — and 3 other queued features want both |
| Seraph | **0 new** — it is a *consumer*, and the best available test |
| Module gate | **1 decision** (tier limits) + closes a fail-open that already exists |
| Leaf | **4 UI pieces**, on an engine that is already built |

> **The feature is mostly not a feature.** Walk it down and it turns out to be four UI pieces sitting on top of work `R1` is already doing for other reasons. **Built leaf-first it would have looked like a week of new plumbing — and would have produced a fifth hand-rolled provisioning path.**

**That is the argument for the method, measured rather than asserted.** Worth applying to the next feature before estimating it: *what does it need from the kernel, what must it say to core, where does the gate touch it, what does gating decide — and only then, what does the user see?*
